이 글은 [칸반보드 리렌더링 최적화 글](/blog/dnd-kit-rendering-boundary-optimization)의 다음 편입니다. 이전 글에서는 JobSecretary에서 카드를 드래그할 때 어떤 컴포넌트가 반복해서 실행되는지 측정하고, 카드 콘텐츠와 드래그 연결을 나누어 개선했습니다.

이번 글에서는 그 내용을 다시 분석하지 않습니다. 대신 한 프로젝트에서 발견한 이상한 동작을 어떻게 dnd-kit 저장소의 재현 가능한 문제로 바꾸고, 테스트와 Pull Request를 거쳐 병합까지 연결했는지를 기록합니다. 결과물은 [dnd-kit PR #2135](https://github.com/clauderic/dnd-kit/pull/2135)입니다.

## 오픈소스 기여의 시작은 “불편하다”를 좁히는 일이었습니다

처음에는 다음처럼 생각하기 쉽습니다.

> dnd-kit을 사용하다 보니 드래그 상태가 가끔 화면에 늦게 반영된다.

이 문장만으로는 라이브러리의 문제인지, 앱의 사용 방법 문제인지, 개발 모드의 특성인지 판단하기 어렵습니다. 그래서 화면 전체가 아니라 **언제 읽은 상태가 다음 변경을 놓치는지**로 범위를 줄였습니다.

최종적으로 정리한 문제는 다음과 같습니다.

> 컴포넌트가 첫 렌더링 뒤에 새로운 드래그 상태 속성을 읽으면, 그 속성이 다음 변경부터 구독되지 않을 수 있다.

여기서 `구독`은 “이 값이 바뀌면 이 화면에 알려 달라”고 연결하는 과정입니다. 값을 계산하는 코드가 틀린 것이 아니라, 변경 알림을 받을 연결이 늦게 만들어지는 문제였습니다.

## 첫 글과 이번 PR의 관계

이전 글의 핵심은 애플리케이션에서 불필요한 실행 범위를 줄이는 것이었습니다. 이번 PR의 핵심은 최신 dnd-kit의 공통 상태 계층에서 **나중에 읽은 속성도 다음 변경을 알 수 있게 하는 것**입니다.

| 이전 글 | 이번 글 |
| --- | --- |
| JobSecretary 화면의 렌더링 범위를 측정 | dnd-kit 내부 상태 구독의 누락을 재현 |
| 컴포넌트 경계와 라이브러리 선택을 조정 | 공통 상태 추적과 adapter 회귀 테스트를 수정 |
| 애플리케이션 코드의 개선 | 라이브러리 코드와 테스트의 개선 |

따라서 이번 수정이 모든 리렌더링 문제를 없애는 것은 아닙니다. 이전 글에서 다룬 앱 구조의 판단은 그대로 남고, 이번 PR은 별도의 상태 구독 문제를 해결합니다.

## 재현 코드를 가장 작게 만들기

문제를 저장소에 전달하려면 내 프로젝트 전체를 복사하는 대신, 동작을 설명하는 작은 예제가 필요합니다. 이번 재현은 드래그 상태를 처음에는 숨겼다가 다음 렌더링에서 보여주는 방식으로 만들었습니다.

```tsx
const sortable = useSortable({id, index});

return (
  <article>
    <h3>{title}</h3>
    {showDragState && (
      <span>{sortable.isDragSource ? "Dragging" : "Idle"}</span>
    )}
  </article>
);
```

확인 순서는 네 단계였습니다.

1. 처음에는 `isDragSource`를 읽지 않은 상태로 항목을 렌더링합니다.
2. `Show drag state` 설정을 켜서 다음 렌더링부터 해당 속성을 읽습니다.
3. Item 1을 드래그합니다.
4. 상태가 `Idle → Dragging → Idle`로 바뀌는지 확인합니다.

수정 전에는 두 번째 단계에서 속성 이름이 기록되더라도, 그 속성이 실제 변경 알림 목록에 바로 들어가지 않을 수 있었습니다. 그래서 화면은 새 속성을 읽었지만 드래그가 시작되고 끝나는 순간을 알림받지 못했습니다.

이렇게 재현하면 “dnd-kit이 이상하다”가 아니라 “첫 렌더링 이후 새로 읽은 signal 속성이 다음 변경을 구독하지 못한다”라고 설명할 수 있습니다. 오픈소스 리뷰에서 이 차이는 매우 중요합니다.

## 코드를 따라가며 원인을 확인한 방법

최신 dnd-kit은 공통 상태 계층과 framework별 adapter로 구성되어 있습니다. React 코드는 상태를 직접 전부 관리하는 대신, adapter를 통해 공통 `Signal` 값을 화면에 연결합니다.

처음 보는 용어는 다음처럼 이해했습니다.

- **Signal**: 값이 바뀌면 연결된 화면에 알림을 보내는 상태 상자
- **Proxy**: 객체 속성을 읽는 동작을 가로채 어떤 속성을 읽었는지 기록하는 JavaScript 기능
- **effect**: 기록된 속성이 바뀔 때 다시 실행되는 연결
- **커밋**: React가 계산한 결과를 실제 화면에 반영한 순간

재현 코드에서 `sortable.isDragSource`를 읽으면 Proxy가 그 속성을 기록합니다. 문제는 기록된 속성을 effect가 언제 구독 목록에 추가하느냐였습니다. 새 속성을 읽은 렌더링과 구독 목록을 갱신하는 시점이 어긋나면서, 다음 상태 변경을 놓칠 수 있었습니다.

## 실제로 바꾼 내용

PR의 수정 방향은 “렌더링할 때마다 모든 상태를 다시 구독하자”가 아니었습니다. 대상별 추적기와 effect를 유지하면서, 새로 읽힌 속성이 확인될 때만 구독 목록을 갱신하는 방식이었습니다.

```text
렌더링 중 새 속성 읽기
        ↓
Proxy가 읽은 속성 기록
        ↓
커밋 이후 effect의 구독 목록 갱신
        ↓
다음 상태 변경부터 화면에 알림
```

구체적으로는 다음 동작을 함께 다뤘습니다.

- 각 대상의 tracker와 signal effect를 렌더링 사이에도 유지
- React에서는 커밋 이후 새 의존성을 반영
- Vue·Solid·Svelte에서는 각 adapter의 생명주기에 맞춰 지연 갱신
- Proxy를 여러 번 읽어도 비교 기준값이 사라지지 않도록 보존
- 대상이 바뀌거나 컴포넌트가 해제될 때 구독과 예약된 갱신을 정리
- 알림을 발생시키는 값이 자기 자신을 다시 구독하지 않도록 분리
- React Strict Mode와 동기 업데이트 동작을 유지

처음 재현한 것은 React였지만, 공통 상태 계층을 사용하는 다른 adapter에서도 같은 종류의 누락이 생길 수 있었습니다. maintainer 리뷰를 거치며 수정과 회귀 테스트가 네 framework로 확장된 이유입니다.

## 테스트를 먼저 고정한 이유

오픈소스 수정에서 테스트는 “내 컴퓨터에서 동작했다”는 증명이 아니라, 문제가 무엇인지 남기는 설명서 역할을 합니다.

이번 PR에는 다음 검증이 들어갔습니다.

- `Show drag state`를 켠 조건부 상태 Storybook 예제
- 포인터 드래그와 키보드 드래그 회귀 테스트
- React hook 테스트
- Vue·Solid·Svelte adapter 공통 회귀 테스트
- 새 속성의 늦은 읽기, 객체를 반환하는 getter, batching, 구독 정리 테스트
- 일반 모드와 Strict Mode에서의 lifecycle 확인

특히 “Item 1을 드래그했을 때 `Idle → Dragging → Idle`이 보여야 한다”는 기대 결과를 코드로 고정했습니다. 내부 구현이 나중에 바뀌어도 사용자가 보는 약속은 유지할 수 있습니다.

## PR 설명은 영어보다 구조가 먼저였습니다

PR은 영어로 작성했지만, 긴 문장을 잘 쓰는 것보다 관찰 가능한 내용을 네 묶음으로 나누는 데 집중했습니다.

```md
## Problem
When a component reads a signal property after its initial render,
the property can be tracked without being subscribed to future updates.

## Change
Retain one effect per target and refresh its dependencies after the
new property is committed.

## Validation
Add conditional-state, pointer, keyboard, and adapter regression tests.

## Scope
This fixes late signal reads. It does not remove every render caused by
an application's component structure or Context usage.
```

한국어로 먼저 문제·변경·검증·범위를 정리한 뒤 짧은 영어로 옮기면 됩니다. 문법보다 재현 단계와 기대 결과가 분명한지가 더 중요합니다. 코드 리뷰어가 바로 실행할 수 있는 명령과 테스트 이름을 적는 것도 도움이 됩니다.

## 리뷰를 거치며 기여 범위가 넓어졌습니다

처음에는 React adapter에서 재현한 문제와 수정 방향을 중심으로 PR을 만들었습니다. maintainer 리뷰를 통해 다음 질문을 확인했습니다.

- 공통 상태를 사용하는 다른 framework에서도 같은 문제가 생기는가?
- 새 객체를 반환하는 getter가 effect 갱신 루프를 만들지 않는가?
- 대상 교체와 unmount 시 예약된 구독이 남지 않는가?
- Strict Mode에서 effect 정리가 두 번 실행되어도 안전한가?

이 질문에 답하는 과정에서 Vue·Solid·Svelte adapter 테스트와 공통 changeset이 추가됐습니다. 개인 프로젝트에서 시작한 작은 재현이 저장소 전체의 회귀 테스트로 확장된 단계입니다.

## 병합 후 무엇이 달라졌나요?

[PR #2135](https://github.com/clauderic/dnd-kit/pull/2135)는 2026년 9월 12일 `clauderic:main`에 병합됐습니다. PR 페이지에 기록된 최종 검증은 다음과 같습니다.

- build task 16개 통과
- unit test 150개 통과
- Chromium 테스트: React 70개, Vue 26개, Solid 26개, Svelte 26개
- TypeScript·Prettier·`git diff --check` 통과
- 일반 모드와 Strict Mode의 구독 정리 및 동기 업데이트 확인

changeset에는 `@dnd-kit/react`, `@dnd-kit/vue`, `@dnd-kit/solid`, `@dnd-kit/svelte`와 공통 패키지 등 10개 패키지가 다음 버전에서 patch release를 받도록 기록됐습니다.

여기서 병합과 배포를 구분해야 합니다. PR이 `main`에 들어간 것은 확인됐지만, 실제 서비스에 적용하려면 사용 중인 패키지 버전의 release와 changelog를 확인하고 업그레이드해야 합니다.

## 처음 기여할 때 따라 할 순서

1. 내가 만든 화면에서 재현 가능한 동작을 한 문장으로 씁니다.
2. 프로젝트 전체가 아닌 최소 재현 코드를 만듭니다.
3. 수정 전에는 실패하고 수정 후에는 통과하는 테스트를 만듭니다.
4. 저장소의 contributing 문서와 기존 PR의 설명 구조를 읽습니다.
5. 변경 범위를 한 기능에 묶고, 다른 framework나 환경에 영향이 없는지 확인합니다.
6. PR 본문에 문제·변경·검증·범위를 짧게 적습니다.
7. 리뷰에서 질문이 나오면 방어하기보다 재현과 테스트를 추가해 답합니다.

처음부터 라이브러리 전체를 이해할 필요는 없습니다. 내가 관찰한 동작을 저장소의 테스트로 번역하는 것부터 시작하면 됩니다.

## 자주 묻는 질문

### 이전 글의 리렌더링 문제도 이번 PR로 해결됐나요?

두 문제는 다릅니다. 이전 글은 JobSecretary의 Context 구독 범위와 컴포넌트 경계를 다뤘고, 이번 PR은 첫 렌더링 뒤 새로 읽은 signal 속성이 이후 변경을 구독하지 못하는 문제를 다룹니다. 앱의 렌더링 비용은 사용하는 구조와 읽는 상태를 따로 측정해야 합니다.

### 개발자가 아니어도 기여할 수 있나요?

문제 재현 영상, 단계별 재현 방법, 기대 결과와 실제 결과를 정리하는 것부터 기여입니다. 코드를 수정할 때도 기존 회귀 테스트 한 개를 읽고 비슷한 실패 케이스를 추가하는 방식으로 시작할 수 있습니다.

### PR이 병합되면 바로 설치하면 되나요?

changeset이 있어도 실제 패키지 release 시점은 별도로 확인해야 합니다. npm에 배포된 버전, changelog, migration 안내를 확인한 뒤 업그레이드해야 합니다.
