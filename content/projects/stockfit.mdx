## 프로젝트 개요

StockFit은 현대그린푸드의 여러 판매 채널과 물류센터에 흩어진 재고를 SKU 단위로 통합해 보여주는 B2B 재고 운영 플랫폼입니다. 운영자는 재고 수량만 확인하는 것이 아니라 판매처별 보유 현황, LOT와 소비기한, 안전재고 미달 여부, 수요예측과 위험 사유를 함께 살펴보고 필요한 대응을 판단합니다.

- **구분**: 팀 프로젝트 (풀스택 4인)
- **기간**: 2026.08
- **담당 범위**: 프론트엔드 공통 기반, 통합 재고 조회·상세·필터, 수요예측·위험 상태, 원천 재고 동기화, 조회·초기 렌더링 성능 개선
- **기술 스택**:
  - 프론트엔드: React 19, Vite, TanStack Query, TanStack Table, Tailwind CSS
  - 백엔드: Java 17, Spring Boot, MyBatis, Spring Batch
  - 데이터·인프라: Oracle, Flyway, RabbitMQ, Redis, Azure Blob Storage
  - 품질 관리: Storybook, Vitest, Playwright, GitHub Actions, Chromatic
- **저장소**: [FrontEnd](https://github.com/kosa11-final-project/FrontEnd) · [BackEnd](https://github.com/kosa11-final-project/BackEnd) · [dummy-data](https://github.com/kosa11-final-project/dummy-data)
- **측정·검증 결과**:
  - 4개 채널 AND 조회로 정리된 Network 캡처에서 목록 **17.99초·요약 30초 취소**, 이후 캡처에서 목록 **726ms·요약 459ms** 관찰
  - 정렬 조건이 포함된 목록 캡처에서 **18.19초**, 이후 캡처에서 **821ms** 관찰
  - 통합 재고 Lighthouse: 성능 **70 → 99점**, TBT **1,650 → 100ms**, CLS **0.049 → 0.036**
  - 초기 Network 캡처: **103건·31.4MB → 15건·4.2MB**, 화면 밖 이미지는 스크롤 시 추가 요청
  - 기준 데이터 스냅샷의 수동 동기화 run #163에서 **33,358건 조회·33,358건 반영·오류 0건** 확인

<blockquote>Lighthouse는 같은 통합 재고 URL(`/inventory?size=100`)의 전후 캡처입니다. Network를 포함해 각 시점의 관찰값이며, 동일 조건을 고정한 반복 벤치마크는 아닙니다.</blockquote>

## 담당 기능

- **프론트엔드 개발 기반**: 네 명의 풀스택 개발자가 같은 방식으로 기능을 추가할 수 있도록 FSD-lite 구조, 디자인 토큰, 공통 HTTP 계층, Storybook, 테스트와 CI 기준을 구성했습니다.
- **통합 재고 조회**: 상품명·SKU·판매처 검색, 채널·물류센터·지역·카테고리·보관유형·위험도 필터, AND/OR 조건, 정렬, 페이지네이션을 구현했습니다. 필터와 상세 상태는 URL에 저장해 새로고침과 링크 공유 후에도 유지되도록 했습니다.
- **재고 상세와 수요예측**: SKU별 판매처·미할당 재고, 보관 위치, LOT, 소비기한, 판매중지일, 가격을 조회하고 D+7·D+14·D+30·D+60·D+90 수요예측과 안전재고 하회 시점을 함께 보여주도록 구성했습니다.
- **위험 재고 판단**: 안전재고 미달, 예상 재고 소진, 소비기한과 판매중지 상태를 바탕으로 위험 등급과 사유를 표시하고, 화면과 동기화 결과에서 같은 기준을 사용하도록 정합성을 보완했습니다.
- **원천 재고 동기화**: 서로 다른 네 종류의 원천 재고를 공통 재고 모델로 반영하고, 실행 등록·진행·완료·실패·복구 대기 상태를 화면에서 확인하도록 연결했습니다.
- **성능과 접근성**: SQL 조회 순서와 인덱스를 조정하고, 라우트·상세 기능·차트·3D·이미지를 필요한 시점에 불러오도록 분리했습니다. 스켈레톤 크기와 표 레이아웃을 고정하고 키보드 탐색, 제목 계층, 색상 대비와 ARIA 관계를 보완했습니다.

#### <span className="text-accent-blue font-bold">문제 상황</span>

#### <span className="text-accent-blue font-bold">해결 과정</span>

- **코드 분할**: `React.lazy`로 페이지를 나누고, 상세·차트·이미지 확대 기능은 열 때 불러왔습니다.
- **큰 3D 라이브러리 관리**: Three.js·React Three Fiber를 사용하는 장면을 별도 모듈로 분리했습니다. 화면 크기·WebGL 지원·데이터 준비 여부를 확인한 뒤 `requestIdleCallback`으로 유휴 시간에 로드하고, 선택한 장면의 3D 모델만 요청했습니다.
- **레이아웃 안정화**: 표·스켈레톤의 열 너비와 행 높이를 맞추고 `table-layout: fixed`를 적용했습니다.
- **접근성**: 탭의 ARIA 관계, 제목 순서, 색상 대비를 보완했습니다.

대시보드 등 다른 화면에도 같은 기준으로 페이지·차트·이미지의 로딩 시점을 나누며 초기 화면을 개선해 나갔습니다.

#### <span className="text-accent-blue font-bold">결과</span>

| 통합 재고 측정 항목 | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| 성능 점수 | 70점 | **99점** |
| TBT · 화면 반응을 막는 시간 | 1,650ms | **100ms** |
| FCP · 첫 콘텐츠 표시 | 0.4초 | **0.3초** |
| LCP · 가장 큰 콘텐츠 표시 | 0.4초 | 0.7초 |
| CLS · 레이아웃 이동 | 0.049 | **0.036** |
| Speed Index | 0.9초 | **0.7초** |
| 접근성 / 권장사항 / SEO | 96 / 96 / 100 | 96 / 100 / 100 |

성능 점수와 TBT는 개선됐으며, LCP는 **0.4 → 0.7초**로 늘어났습니다. 위 지표는 모두 제공된 통합 재고 화면 두 장을 기준으로 정리했습니다.

#### <span className="text-accent-blue font-bold">네트워크 요청 최적화</span>

- **이미지 요청·용량 축소**: 첫 두 행은 우선 요청하고, 나머지는 `IntersectionObserver`로 화면 근처에 올 때 불러왔습니다. 상품 썸네일과 로고·배경 이미지 압축으로 전송량을 줄였습니다.
- **캐시와 요청 취소**: TanStack Query 캐시를 재사용하고, 요약 쿼리 키에서 페이지·정렬 값을 제외해 같은 필터의 요약을 재요청하지 않도록 했습니다. 필터 변경으로 불필요해진 요청은 `AbortSignal`로 취소하고, 동기화 완료 후 관련 캐시를 갱신했습니다.
- **필요할 때만 API 호출**: 상세 창을 열고 해당 탭을 볼 때 LOT·위험도·수요예측을 조회했습니다. 동기화 상태도 실행 중일 때만 확인하고 백그라운드 탭에서는 반복 조회를 멈췄습니다.

초기 Network 캡처는 **103건·31.4MB → 15건·4.2MB**였습니다. 화면 밖 이미지 요청은 스크롤 시점으로 미뤘으며, URL·캐시 조건을 동일하게 통제한 측정은 아닙니다.

### 3. 네 종류의 원천 재고를 한 번만 안전하게 반영하는 동기화 흐름

#### <span className="text-accent-blue font-bold">문제 상황</span>

창고·온라인·오프라인·기타 원천 재고는 식별자와 수량 표현이 서로 달랐습니다. 원천 형식을 그대로 통합 재고 화면에 연결하면 같은 상품이 중복되거나, 재실행할 때 이미 반영한 재고를 다시 더할 수 있었습니다. 여러 운영자가 동시에 동기화를 누르는 상황과 동기화 후 대시보드·통계 스냅샷 중 하나만 실패하는 상황도 처리해야 했습니다.

#### <span className="text-accent-blue font-bold">해결 과정</span>

원천별 파서를 공통 형식으로 바꾼 뒤 SKU, 판매처, 물류센터, LOT 식별자를 해석해 통합 기준 재고에 반영하고, 원천 행의 해시를 이전 반영 해시와 비교해 실제로 바뀐 행만 대상으로 삼았습니다. 같은 `clientRequestId`로 다시 호출되면 기존 실행을 반환하므로, 재시도해도 같은 실행이 중복 등록되지 않습니다.

두 실행이 동시에 재고를 바꾸지 못하도록 Oracle의 행 잠금과 실행 상태를 함께 확인했습니다. 재고 반영과 위험도 재산정은 핵심 동기화 안에서 처리하고, 대시보드와 통계용 집계 데이터 생성은 별도 작업으로 분리해 실패한 작업만 재시도하거나 복구하도록 했습니다.

활성 실행이 있을 때만 프론트엔드가 5초 간격으로 상태를 확인하며, 백그라운드 탭에서는 반복 조회를 멈춥니다. 동기화가 성공하면 재고 목록과 요약, 상세, LOT, 위험도에 사용하던 TanStack Query 캐시를 갱신해 새 결과를 화면에 반영했습니다.

```text
원천 4종 → 형식 정규화 → 변경 행 판별 → 통합 재고 반영 → 위험도 재산정
                                                     └→ 대시보드·통계 스냅샷 작업
```

#### <span className="text-accent-blue font-bold">결과</span>

동기화 실행 이력, 원천별 처리 건수, 오류 건수와 후속 스냅샷 상태를 화면에서 나눠 보여줬습니다. 기준 데이터 스냅샷을 사용한 수동 검증 run #163에서는 원천 **33,358건을 읽어 33,358건을 반영했고 오류는 0건**이었습니다. 같은 요청의 중복 실행을 막으면서도 실패한 후속 스냅샷 task만 다시 처리하므로, 전체 재고 동기화를 처음부터 반복할 필요가 없습니다.

### 4. 네 명이 같은 기준으로 기능을 추가할 수 있는 프론트엔드 기반

#### <span className="text-accent-blue font-bold">문제 상황</span>

프로젝트 초기에 네 명의 풀스택 개발자가 동시에 화면을 만들기 시작하면 폴더 위치, API 호출 방식, 공통 UI와 상태 관리 기준이 빠르게 달라질 수 있었습니다. 기능 구현 속도만 우선하면 페이지가 늘어날수록 수정 범위를 예측하기 어렵고, 새 팀원이 기존 화면의 로딩·오류·빈 상태를 놓칠 가능성도 있었습니다.

#### <span className="text-accent-blue font-bold">해결 과정</span>

엄격한 FSD 전체 규칙 대신 팀 규모에 맞춘 FSD-lite를 적용했습니다. `app → pages → widgets → features → entities → shared`의 의존 방향을 정하고, 한 화면에서만 쓰는 코드는 먼저 페이지에 두되 두 곳 이상에서 같은 의미로 사용할 때만 상위 구조로 분리했습니다.

Axios는 HTTP 요청과 공통 오류 처리, TanStack Query는 서버 상태와 캐시를 담당하도록 역할을 나눴습니다. Storybook으로 공통 UI 상태를 관리하고, 린트·테스트·빌드를 실행하는 CI와 온보딩 문서를 구성했습니다.

#### <span className="text-accent-blue font-bold">결과</span>

API·모델·필터·동기화·테이블·상세 화면의 책임을 분리했습니다. 화면마다 요청·캐시·로딩·오류 처리를 같은 기준으로 적용할 수 있도록 구성했습니다.
